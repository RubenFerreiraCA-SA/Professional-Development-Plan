# Learning & Assessment

**Purpose:** Define how each module is studied and what counts as evidence of competence. Detailed topics and labs belong in the [module files](../README.md#disciplines-and-modules).

## Approach

Plan around **8–10 hours per instructional week**:
1. Study concepts and official guidance.
2. Implement the module's practical lab.
3. Test, troubleshoot and explain the result.
4. Record the outcome and evidence link in the [Study & Evidence Log](05_Study_and_Evidence_Log.md).

Each weekly lab should produce an inspectable output: code, configuration, pipeline run, deployed service, monitoring view, runbook or technical notes.

## Programme outcomes and assessment evidence

| Competence | Suitable evidence |
| --- | --- |
| DevOps delivery and automation | Container images, CI/CD runs, Terraform plans and GitOps reconciliation |
| Cloud infrastructure and security | Network designs, IAM controls, reproducible deployments, cost checks |
| AI integration and operations | Working integrations, evaluation examples, safeguards, monitoring |
| Kubernetes and platform services | Deployments, troubleshooting, templates, self-service workflows |
| Engineering judgement | Short architecture decisions, failure investigations, design trade-offs |

## Completion standard

A module is **complete** when its defined learning objectives and required practical work have been demonstrated, and evidence is recorded. An external certification is tracked separately: completion of a module does not imply an examination has been passed.

Assess working results for **correctness, security, repeatability, reliability, maintainability and explanation**. If a lab fails, document the cause, remediation and retest. Use the original syllabus's **7% / 20% / 13% / 27% / 20% / 13% DevOps weights**; do not replace them with a new rubric without author agreement.
