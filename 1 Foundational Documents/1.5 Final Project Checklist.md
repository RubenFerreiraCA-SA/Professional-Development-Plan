# Final Project Checklist — Harbour IDP

Use this page as the **spine of the recommended Final Project**: one running system (**Harbour**) that grows module by module into a small **Internal Developer Platform**.

It complements the [Final Project guide](1.4%20Final%20Project.md) (purpose and completion standard) and the [Progress and Evidence Log](../2%20PDP%20templates/2.4%20Progress%20and%20Evidence%20Log.md) (session-by-session notes). Tick a row when the **platform capability** exists and you can show evidence — not when the calendar week ends.

The project is **recommended, not compulsory**. If you adapt or skip modules in your [Capacity Planner](../2%20PDP%20templates/PDP%20Capacity%20Planner.xlsx), mark those rows `Skipped` / `Adapted` and keep equivalent evidence.

## Progressive checklist

| ☐ | Module | What Harbour / the IDP gains | Minimum evidence to keep |
| --- | --- | --- | --- |
| ☐ | **D01** | Governed monorepo (or defended alternative): ownership boundaries, protected default branch, contribution path, secret hygiene | Repo structure, CODEOWNERS/approvals (or documented gap), ADR, reviewed change to `infra/` or `deploy/` |
| ☐ | **D02** | Safe history practice for the same repo: conflict/recovery playbook the team can reuse | Documented recovery on a disposable branch/clone; regression hunt (e.g. bisect) with notes |
| ☐ | **D03** | Runnable **Harbour API** (+ dependency) as a hardened container contract | Multi-stage image, Compose (or equivalent), health endpoint, image digest, build instructions, SBOM/vuln notes |
| ☐ | **D04** | Trusted path from reviewed change → tested immutable artifact → simple promotion | PR/MR pipeline, failing-check gate, digest-addressed release, provenance to commit SHA |
| ☐ | **D05** | Reusable **infra** offering: environments via Terraform modules, remote state, reviewable apply | Two environments, locked state, plan-in-CI + approved apply, app reachable under network/IAM controls |
| ☐ | **D06** | Declarative **deploy/** reconciled by GitOps; rollback and drift recovery | Controller + desired state, promotion/rollback demo, recovery notes from an isolated cluster |
| ☐ | **D07** | Vendor-neutral observability on the request path: telemetry, SLIs/SLOs, alert + runbook | Instrumented path, collector pipeline, SLOs, deliberate failure investigation write-up |
| ☐ | **D08** | Operable monitoring service (Datadog or documented equivalent) other teams can use | Dashboards, correlated traces/logs, tested monitors, second-service onboarding package |
| ☐ | **C01** | Solid ops baseline: Linux/network literacy applied to how Harbour is reached and troubleshot | Network/path notes for the app, diagnostic commands/runbook for connectivity failures |
| ☐ | **C02** | Cloud landing zone foundations for Harbour (identity, network edges, cost awareness) | Account/IAM/network sketch + implemented baseline matching your stack |
| ☐ | **C03** | Resilient cloud architecture: Harbour infra hardened for failure, access and cost | Architecture ADR, HA/backup/limit choices verified in `infra/`, cost controls noted |
| ☐ | **A01** | Scoped AI capability on Harbour (e.g. read-only diagnostics/assist) with evaluation | Feature behind clear boundaries, test cases, eval results, documented limitations |
| ☐ | **A02** | Controlled agent/orchestration path (if in scope) that cannot silently change prod | Tool permissions, human/approval boundaries, failure-mode notes |
| ☐ | **A03** | Operable AI piece: versioning, monitoring, cost/safety for the Harbour AI feature | Deployment/config for the model path, basic LLMOps checks, rollback or disable switch |
| ☐ | **P01** | Harbour workloads expressed as sound Kubernetes primitives | Manifests/Helm/Kustomize (as chosen), probes, resources, local/cluster demo |
| ☐ | **P02** | Day-2 platform ops: namespaces, access, upgrades/backup habits for the Harbour cluster | Ops runbook, RBAC/quotas (as scoped), recovery exercise evidence |

**Status tip:** replace `☐` with `☑` when done, or note `Skipped` / `Adapted: …` in your Progress Log.

## Discipline milestones

After each discipline, Harbour should be able to show a larger platform story:

| Milestone | Harbour can… |
| --- | --- |
| **End of DevOps** | Accept a reviewed change, build a trusted image, provision/deploy through code and GitOps, and investigate with telemetry |
| **End of Cloud** | Run on intentional cloud foundations with clearer IAM, networking, resilience and cost boundaries |
| **End of AI** | Offer a limited, evaluated AI aid with operational safeguards (if included in your PDP) |
| **End of Platform** | Let another developer follow a golden path onto the platform and see health, controls and recovery |

Align these dates with the discipline milestones in your Capacity Planner.

## Final demonstration checklist

Before you call the Final Project complete, confirm the [completion standard](1.4%20Final%20Project.md):

| ☐ | Demonstration |
| --- | --- |
| ☐ | Another developer can start from the template or Harbour service docs and contribute safely |
| ☐ | A reviewed change triggers automated build/test and produces a traceable artifact |
| ☐ | An approved environment is selected or provisioned through code and the service is deployed |
| ☐ | Health is visible; a failure can be investigated and recovered from with a documented path |
| ☐ | Security and access controls for the demo are explained (and gaps are honest) |
| ☐ | Any AI component has purpose, evaluation, limits and safeguards explained |
| ☐ | Repo has no real secrets; limitations and cost choices are written down |
| ☐ | Short architecture decisions + PDP reflection (what you achieved / deferred / learn next) |
