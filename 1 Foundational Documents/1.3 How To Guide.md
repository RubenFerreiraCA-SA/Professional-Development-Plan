# Programme Guide

Use this framework to build **your own** Platform Engineering PDP. The [Overview](1.1%20Programme%20Overview.md) explains the destination; the [Course Outline](1.2%20Course%20Outline.md) shows the sequence. This guide explains what to do with them.

## 1. Personalise the plan

Before starting, decide:
- **Starting point:** Which skills do you already have, and where are your gaps?
- **Outcome:** Which Platform Engineering capabilities or specialisations matter most to you?
- **Capacity:** How many hours can you study consistently? Plan around the **estimated hours for each module**, adjusting for your experience and capacity.
- **Timing:** Choose your own start date, breaks and milestones. Estimated study hours are a guide, not a fixed calendar schedule.
- **Evidence:** Where will you store lab work, code and notes?
- **Scope:** Which disciplines or modules are in your PDP? Mark optional tracks (especially **AI**) explicitly if you exclude them — that is a valid complete pathway.

Work through the [PDP templates](../2%20PDP%20templates/):

1. [Personal Profile](../2%20PDP%20templates/2.1%20Personal%20Profile.md) — goals and scope
2. [Capacity Planner](../2%20PDP%20templates/PDP%20Capacity%20Planner.xlsx) — hours per week → duration and module dates ([method](../2%20PDP%20templates/2.2%20Capacity%20and%20Timeline.md))
3. Module schedule in the workbook (or [Markdown schedule](../2%20PDP%20templates/2.3%20Module%20Schedule.md))
4. [Progress and Evidence Log](../2%20PDP%20templates/2.4%20Progress%20and%20Evidence%20Log.md) — while you study
5. [Final Project Checklist](1.5%20Final%20Project%20Checklist.md) — acceptance criteria for what the platform can do

## 2. Three views of progress (keep them distinct)

You maintain three complementary views. Do not collapse them into one tracker.

| Level | Artefact | Question it answers | Update when… |
| --- | --- | --- | --- |
| **Plan** | [Capacity Planner](../2%20PDP%20templates/PDP%20Capacity%20Planner.xlsx) | **When** do I expect to complete each module and the pathway? | Weekly capacity, start date, buffer, or `Include` scope changes |
| **Learning** | [Progress and Evidence Log](../2%20PDP%20templates/2.4%20Progress%20and%20Evidence%20Log.md) | **What** have I learned, built and recorded? | After each study session or Practical Assessment attempt |
| **Platform** | [Final Project Checklist](1.5%20Final%20Project%20Checklist.md) | **What can Harbour / the IDP demonstrably do?** | Only when that row’s **acceptance criterion** is met |

**How they connect:**

```text
Capacity Planner          Progress Log              Final Project Checklist
(scope + dates)           (sessions + links)        (acceptance / platform capability)
        │                        │                              │
        │  sets target timing    │  learning Complete when      │  tick only when the
        │  and Include Yes/No    │  Course Detail outcomes      │  acceptance criterion
        │                        │  are demonstrated            │  is met (may lag)
        └───────────┬────────────┴───────────────┬──────────────┘
                    │                            │
                    │   if pace drifts →         │  independent of learning
                    │   re-plan dates            │  Complete — do not hold
                    │   (do not fake acceptance) │  the Progress Log open
                    │                            │  waiting on integration
                    ▼                            ▼
              Personal Profile keeps goals, scope and milestone summary
```

Rules of thumb:

- A calendar date in the Capacity Planner is a **forecast**, not a pass.
- **Learning completion and platform acceptance are separate.** Mark a module **Complete** in the Progress Log when its Course Detail / Practical Assessment outcomes are demonstrated, even if Harbour’s integrated checklist row is still open.
- A checklist tick requires the stated acceptance criterion (often a cold run, second-person test or fuller IDP integration), not “I finished the reading” and not merely “Progress Log = Complete.”
- **Optional for the Final Project** is not the same as **optional in the curriculum.** Example: **D08** remains Chapter 8 of the full DevOps syllabus; it is optional only for personalised Final Project acceptance (you may use a D07-equivalent ops path instead). Unticked Final Project–optional rows do **not** mean an incomplete Final Project; skipping them does mean you have not completed the full eight-chapter DevOps curriculum unless you study them anyway.

## 3. Follow the learning cycle

For each learning activity:

1. **Learn** the concepts and read the prescribed materials.
2. **Build** the lab or practical deliverable.
3. **Verify** that it works, including failures and recovery where relevant.
4. **Record** a link to the result in the Progress Log, plus what you learned.
5. **Accept** the matching Final Project Checklist row when its criterion is true — that step may come later than learning completion if integration work remains.

Aim to complete practical work, not just read about it. If a topic requires more time, adjust the Capacity Planner rather than skipping the lab or lowering the acceptance bar silently.

## 4. Build towards the Final Project

The recommended [Final Project](1.4%20Final%20Project.md) is a **generic Internal Developer Platform** that connects the disciplines you included. Adapt or replace it with equivalent practical work if your PDP calls for something different.

The [Final Project Checklist](1.5%20Final%20Project%20Checklist.md) is the **specification**: after each in-scope module, what Harbour must gain, the pass criterion and the evidence to keep.

| Stage | Typical project contribution | Notes |
| --- | --- | --- |
| DevOps | Repository, containerised app, CI/CD, Terraform, GitOps and observability | Full curriculum is D01–D08; D08 is optional only for Final Project acceptance if D07-equivalent ops are documented |
| Cloud | Secure infrastructure, IAM, networking, cost controls and resilience | |
| AI | Limited, tested AI feature such as read-only diagnostics | **Optional** for both personalised pathway and Final Project — exclude freely in your PDP |
| Platform | Kubernetes, self-service templates, golden paths and developer experience | |

Each module can include its own **Practical Assessment**; those detail the bar where published. Keep the project reproducible and document important design decisions. Sample data and non-confidential environments are sufficient.

## 5. Track real progress

Use the Progress and Evidence Log (or the Progress Log sheet in the Capacity Planner) for session-level records:

| Date | Module | Hours spent | What you completed | Evidence link | Status | Next step |
| --- | --- | ---: | --- | --- | --- | --- |
| | | | | | | |

Mark **learning** complete in the Progress Log when you can demonstrate the module’s Course Detail objectives / Practical Assessment — including when the integrated Harbour capability is not ready yet. Mark the **platform** row on the Final Project Checklist only when its acceptance criterion passes. Either order is fine; do not block learning Complete on checklist acceptance. If actual pace diverges for more than a couple of weeks, update the Capacity Planner — leave checklist acceptance unchanged until the criterion is truly met.

## 6. Add optional certifications

Certifications can help validate skills, but they are **not required** to complete the programme. Select exams that match your goals, check current provider requirements, and schedule preparation alongside—rather than instead of—the practical work.

## 7. Adapt without losing the foundation

Adjust dates, pace, optional credentials and areas of deeper specialisation to fit your needs. Keep track of any topics you omit or replace in the Personal Profile and Capacity Planner `Include` column, and mark those Final Project Checklist rows `N/A — out of scope` or `Adapted: …`. Be explicit whether an omission is from the **Final Project only**, from the **full curriculum**, or both — e.g. skipping D08 for IDP acceptance while still studying it as Chapter 8.
