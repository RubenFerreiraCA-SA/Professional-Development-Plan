# Final Project — Internal Developer Platform

## Purpose

The **Final Project** gives developers a practical way to demonstrate the skills developed through their personalised PDP. Rather than completing unrelated exercises, the recommended pathway builds towards a working **Internal Developer Platform (IDP)**.

The project is **recommended, not compulsory**. Developers may adapt its scope, use a different application or choose equivalent practical work that better supports their PDP goals. It does not award a qualification or certification.

## What are you building?

An internal platform that helps a developer take an application from source code to a reliable deployment using reusable, secure, self-service workflows.

A useful demonstration might let another developer create a service from a template, provision an approved environment, deploy through an automated workflow and inspect the application's health—without needing direct access to every underlying infrastructure tool.

Keep the implementation focused. You do **not** need to build a commercial platform, run a large production cluster or implement every possible feature.

## How the project develops

| Discipline | Contribution to the final project | Evidence |
| --- | --- | --- |
| **DevOps Engineering** | Repository structure and governance; containerised application; CI/CD; Terraform; GitOps and monitoring | Source repository, reviewed changes, repeatable builds, deployment definitions and dashboards |
| **Cloud Engineering** | Cloud networking, IAM, infrastructure deployment, resilience and cost controls | Infrastructure code, architecture decisions and verified environment configuration |
| **AI Engineering** | A limited, useful AI feature, such as read-only operational diagnostics, with evaluation and operational safeguards | Implemented feature, test cases, evaluation results and documented limitations |
| **Platform Engineering** | Kubernetes workloads, reusable service templates, self-service workflows, security policies and developer experience | Working platform demonstration, developer instructions, security/reliability checks and feedback |

Each discipline should extend the same project where practical. Modules can still have their own **Practical Assessments** that exercise a narrower set of skills.

## Suggested final demonstration

Show that a developer can:

1. Start from a documented template or existing service and understand how to contribute safely.
2. Trigger an automated build and test process from a reviewed change.
3. Provision or select an approved environment through code and deploy the service.
4. Observe application health and understand how to investigate or recover from a failure.
5. Demonstrate the relevant security and access controls.
6. Explain any AI component's purpose, evaluation, limitations and safeguards, if included in their PDP.

The technical choices are flexible: select tools that fit the learner's goals, constraints and budget.

## What counts as completion?

The aim is **demonstrable capability**, not a perfect product. A completed project should have:

- **Working evidence:** a reproducible demonstration, source code and configuration.
- **Clear decisions:** a short explanation of key architectural trade-offs.
- **Safe operation:** reasonable access controls, no committed secrets and documented limitations.
- **Usable instructions:** enough information for another developer to run or evaluate the solution.
- **A reflection against the PDP:** which objectives were achieved, which were not and what to learn next.

The project may be delivered in stages, and it may remain deliberately limited in scope. Completing the project is not a substitute for external certifications.

## Practical guidance

Use a sample application and non-confidential data. Prefer low-cost or local environments where possible, remove unused paid resources and never publish live credentials. Keep links to code, demonstrations and key outcomes in the developer's personal PDP.
